## 一、现状体检（实测数据）

### 1.1 数据产出节奏

```
文件名格式：{YYYYMMDDHHmmss}_{机台号}_{Utility|WORKINFO}.CSV
例：20260816201731_M01_Utility.CSV
```

- **每台压机每分钟导出 1 个 Utility + 1 个 WORKINFO**（1440 个/机台/天）
- 样本共 **12 台机**（M01~M12），其中 3 台是主力（跑了 8 天），其余各跑了 2~3 天
- 满产 12 台机：**12 × 1440 × 2 = 34,560 个文件/天**
  （实测两个满产日各 31,407 个，与推算吻合）
- 样本时间跨度：2026-08-16 20:16 ~ 2026-08-24 23:59（9 天）

> 🔴 修正估算：不是"一周两周几万个"，而是**一周约 24 万个、两周约 48 万个**。
> 卡顿的真正元凶不是数据量（实际只有 33 MB），而是**文件数量**——
> 48 万个 × 4KB 簇 = 约 1.9 GB 的磁盘占用，且 Windows 单目录文件数上万后枚举/复制呈指数级变慢。

### 1.2 文件内部结构（关键：极适合合并）

| 类型 | 数量 | 结构 | 单文件 |
|---|---|---|---|
| Utility | 65,468 | 表头 + **1 行**数据（38 列：T.SP/T.PV/…/H1~H21/P1~P6） | ~387 B |
| WORKINFO | 49,301 | 表头 + **1 行**数据（14 列：批号/品名/程式/尺寸/时间…） | ~234 B |

- 每个文件都是 **2 行**（表头 1 行 + 数据 1 行），表头被重复存储了 11 万次
- **全部纯 ASCII、无 BOM、无中文** → 编码零风险
- 体检结果：**0 个空文件、0 个异常文件**，两种表头 11 万份**完全一致**
- ⚠️ 小坑：数据行比表头**多 1 列**（行尾多余逗号），合并时需按表头列数截断，否则所有列会错位

### 1.3 WORKINFO 冗余度极高（额外压缩空间）

一台主力机的 8,638 个 WORKINFO 文件，去重后只有 **20 个不同的批次**。
变化字段仅 `HTime` / `Progress Time` / `Remaining Time` 三个，其余 11 列在一批内完全不变。

→ 这意味着 WORKINFO 可以按"批次主档"（20 行）+ "进度时序"（8,638 行）两级存储，
进一步压缩。但**建议本期不做**，保持"一行一分钟"的通用结构，降低复杂度和出错面。

## 二、现有脚本解读（读懂了什么）

现有脚本是 **压机数据合成器 V3.1**（`<legacy-workspace>\Code.ps1`，86 KB，约 2,200 行）。
它的任务链条是：

```
① 扫描 CSV 文件名 → 解析出 {时间戳, 机台号, 类型}
② WORKINFO → 建立「批号定义」（机台 + LotNo + Start Time），去重后按机台+开始时间排序
③ Utility → 按「文件名时间戳」归属到批号：
      找 StartTime ≤ utilityTime 的「最大 StartTime」那个批次
      （早于所有批次的 fallback 归入第一个批次）
④ 同批号的所有 Utility 行合并 → 写出「分机批号合成 Excel」
⑤ 再从合成 Excel 生成：料温汇总表 + 曲线图（21 条层温曲线，按月配色）
```

**核心关联逻辑**：WORKINFO 提供"批次边界"，Utility 靠**时间戳落在哪两个批次之间**来归批。
它还内建了 `T.SP 跳变检测`来判定批次真实结束时间、`300 分钟时长校验`、`曲线点数 >500 自动抽样到 300` 等工程细节——
这些是**真正有价值的业务逻辑，应当保留复用**。

### 现有脚本的两个硬约束（现场跑不了）

| 约束 | 说明 | 现场影响 |
|---|---|---|
| `New-Object -ComObject Excel.Application` | 全程靠 Excel COM 写 xlsx | 🔴 现场无 Excel → **完全跑不了** |
| 控制台 `Read-Host` 交互 + 模板 xlsx 依赖 | 需要 `压机料温温度模版.xlsx`、`曲线图模版.xlsx` | 🔴 模板/COM 都不可用 |

> 但这不影响本次目标：**合并阶段本来就该在"无 Excel"的现场做，分析出图拿回办公机做**。
> 正好分工：现场只做纯文本合并（减文件数），回来再跑合成器出图。

### 现场环境适配性（已验证可用）

| 需求 | 现场方案 | 验证 |

| 执行 PowerShell | `powershell -ExecutionPolicy Bypass -NoProfile -File Code.ps1` | ✅ 现有 bat 就是这么写的 |

## 三、方案设计

### 3.1 合并规则

**合并粒度：按「日期 + 机台 + 类型」合并成一个文件**（推荐方案 A）

```
20260817_M01_Utility.CSV     ← 该机台当天所有 Utility 行（约 1440 行，约 500 KB）
20260817_M01_WORKINFO.CSV    ← 该机台当天所有 WORKINFO 行
```

- 表头只写 1 次
- **新增 `SrcFile` 列**，记录每行来自哪个原始文件名 → **保住可追溯性，也保住后续批号归批所需的原始时间戳**
- 行内数据按时间戳升序排列

| 方案 | 规则 | 样本结果 | 评价 |
|---|---|---|---|
| **A（推荐）** | 日期 + 机台 + 类型 | 95 个 | ✅ 单文件 ~500 KB、~1440 行，Excel 秒开，远低于 104 万行上限 |
| B | 日期 + 类型（所有机台拼一起） | 18 个 | ⚠️ 需增加机台列，但列结构变了，兼容性差 |
| C | 月份 + 机台 + 类型 | 24 个 | ⚠️ 单文件 ~4 万行 / 14 MB，Excel 打开明显变慢，且跨天故障排查不便 |

### 3.2 安全设计（这是重点，逐条都是防翻车）

| # | 机制 | 说明 |
|---|---|---|
| S1 | **只读源文件** | 合并阶段只用 `File.ReadAllText` 读取，绝不修改、绝不移动原文件 |
| S2 | **安全时间窗** | 默认只处理**文件名时间戳早于今天 00:00** 的文件；当天正在写的文件**一律不碰**（避开与压机写入的竞态） |
| S3 | **行数校验才转正** | 先写 `xxx.csv.tmp`，校验「合并行数 == 参与合并的源文件数」且「源文件数 > 0」后才转正；校验失败保留 .tmp 并告警，**绝不静默产出残缺文件** |
| S4 | **默认不删除** | 删除必须显式加 `-DeleteSource` 开关；默认是只合并、不动原文件 |
| S5 | **删除 = 逐组原子操作** | 合并一组→行数校验→只删这一组→下一组；中断时已删的必已安全合并，剩下的原样不动，重跑即续 |
| S6 | **空跑预演 Preview 模式** | 只统计、不写不删，先看看会处理多少文件 |
| S7 | **单点失败不中断** | 单个文件读取失败 → 记日志跳过，整体继续；失败清单落日志 |
| S8 | **完整日志** | 每次运行写 `Logs\RUNLOG_*.txt`，记录：处理数、分组数、失败清单、耗时、体积；删除清单另存 `DELETED_*.txt` |
| S9 | **不做的事** | 不改系统设置、不写注册表、不联网、不装任何东西、不碰非 CSV 文件、不递归删除 |
| S10 | **路径白名单** | 只在用户指定的源目录内操作，删除前校验文件必须匹配 `^\d{14}_.+_(Utility|WORKINFO)\.CSV$` 且位于源目录树下 |

### 3.3 执行流程（现场用法）

```
[首次] U 盘拷入「Press CSV Merger」文件夹到现场电脑（含 .bat + .ps1）
       ↓
  双击「0_CheckEnv.bat」→ 确认环境没问题（只读检查）
       ↓
  双击「1_Preview.bat」→ 看看会处理多少文件、产出多少（不写不删）
       ↓
  双击「2_Merge.bat」→ 合并昨天及更早的文件，产出到「_Merged\」
       ↓
  看 Logs 确认「零失败」
       ↓
  双击「3_MergeClean.bat」→ 合并 + 删除已安全合并的源文件（需输入 Y 确认）
       ↓
  U 盘拷走「_Merged\」（95 个文件 / 21 MB，秒传）
```

**日常**：注册每日排程自动跑（默认 08:00），或每天手动跑一次「3_MergeClean.bat」，约 45 秒 + 几秒。

> ⚠️ **首次运行**面对的是历史积压（可能几十万文件），预计 10~30 分钟。
> 工具内置 30 分钟安全时限会自动停在安全点，下次运行继续，无需手动分批。

## 五、关键风险与对策

### 🔴 R1：PowerShell 中文脚本必须带 BOM（已踩坑）

**现象**：本次原型首次运行直接 `ParserError` 崩溃——PS 5.1 按系统 ANSI(936/950) 解析无 BOM 的 UTF-8 文件，
中文字节被误读成引号，整段语法崩坏。
**对策**：交付脚本一律存 **UTF-8 with BOM**。写入时用 `utf-8-sig`。
（最终交付版进一步把界面文字全部改成纯 ASCII，从根上规避该问题。）

### 🔴 R2：合并后的 CSV **不能直接喂给现有合成器**（最重要）

现有合成器有两处假设会失效：

| 位置 | 现状假设 | 合并后失效原因 |
|---|---|---|
| `Assign-UtilityToBatch` | **一个 Utility 文件 = 一个时间戳 = 归一个批号** | 合并后一个文件含 1440 行，文件名只有 1 个时间戳 → 整批归错 |
| `Build-BatchDefinitions` | 每个 WORKINFO 文件**只读第 1 行**（`Data[0]`） | 合并后一个文件 1440 行 → 只取首行 → **一天只剩 1 个批号定义，批次全丢** |

**对策（推荐路线甲）**：给合成器加一个「合并模式」适配层，改动量约 30~50 行：
- Utility 归批时，不再用文件名时间戳，改用合并文件里的 **`SrcFile` 列**反推时间戳（合并器已预留这一列，就是为了这个）
- WORKINFO 改为**遍历所有行**建批号定义（现有代码本就有 `Machine+LotNo+StartTime` 去重，天然支持多行）
- 其余逻辑（T.SP 跳变判批尾、300 分钟校验、层温配色、曲线抽样）**完全不动，原样复用**

> 备选路线乙：在合并阶段就按批号拆好文件。但那等于把分析逻辑搬到现场无 Excel 的机器上跑，不划算。

### 🟡 R3：脚本运行时压机仍在写文件
→ S2 安全时间窗（只处理昨天及更早）+ 文件名时间戳冷却期（默认 10 分钟）。

### 🟡 R4：现场磁盘可能已满
合并只需额外 21 MB 级空间，可忽略。
若磁盘告急，可让合并结果**直接写 U 盘**（`-Out U:\xxx`），绕过本机空间问题（代价：跨盘复制，慢一些）。

### 🟡 R5：首次运行耗时长（10~30 分钟）
→ 工具内置 30 分钟安全时限，自动停在安全点；或安排在停机时段；或先把历史数据拷回办公机合并（办公机快得多）。

### 🟢 R6：误删风险
→ S4/S5/S10 三重保护：默认不删 + 逐组原子（校验通过才删这一组）+ 删除前白名单复核。原始文件名信息完整保留在 `SrcFile` 列，即便极端情况也能从合并文件反推。

### 8.2b 自动化（追加）

用 Windows 内建**工作排程器**，一键注册，无需手动点界面：

- `5_InstallSchedule.bat` → 默认每天 08:00，可改时间，全程后台静默
- 优先用 PowerShell `ScheduledTasks` 模块注册（`schtasks.exe` 为备用方案）
- 已设 **StartWhenAvailable**（错过时间开机后自动补跑）、不被电池策略挡住、超时上限 6 小时
- `6_RemoveSchedule.bat` 一键取消

**端到端实测**（本机）：注册 → 手动触发 → 960 个文件合并成 5 个 + 原件清零，
**耗时 2.4 秒，返回码 0，零失败**。

⚠️ **前提**：电脑需处于「开机且已登录 Windows」状态排程才会跑。
若压机会每天关机/登出，需让电脑保持登录、设自动登录，或请信息单位改为「不管用户是否登录都执行」。

**配套的自动模式保护**：`-NoPause`（自动模式）下脚本绝不等待任何输入——
若配置文件的 `Src=` 为空会直接报错结束，避免排程永久卡死。

### 8.4 实测中发现并修掉的 4 个问题

1. **删除极慢**：逐档 `[System.IO.File]::Delete` 约 **54 ms/个**（8,860 个要 8 分钟）。
   改用 `cmd del` 分批批量删除（60 个/批）→ **快约 25 倍**，并保留失败回退。
2. **中断残留孤儿**：原幂等逻辑会把"已合并但删除失败"的文件永久跳过。
   已修：删除模式下，若该档标记已存在于合并档的 SrcFile 栏，仍排入清理清单。
3. **PowerShell 陷阱**：函数 `return` 一个 HashSet 会被管道**枚举展开**，全删完（空集合）时变成 `$null` 导致崩溃。
   已修：`return ,$set`（一元逗号防展开）。
4. **配置文件编码**：原按单一编码读写，**简体中文路径会变成问号**。
   已修：智能识别（UTF-8 BOM → 系统 ANSI → 无 BOM UTF-8），写入统一用 UTF-8 with BOM。

> 另修正：预演模式的耗时预估曾显示 149 分钟（实际约 2.5 分钟）——单位换算 bug，已修。
